# 企业通用 AI Native 改造项目整体方案

版本：v0.2。日期：2026-11-04。状态：整合后的当前工作方案，供选择首个业务入口和后续决策使用；本轮仅整理文档，不启动代码或客户系统接入。

完整愿景见[项目完整构想](../01-愿景与定位/项目完整构想.md)，授权与假设见[状态登记](../06-决策与研究/整合决策与待验证假设.md)。本版接替 [v0.1](2026-11-03-project-plan-v0.1.md)作为当前工作方案，保留其原文和七项交付能力。

## 1. 定位与本版变化

长期目标：让 AI 持续理解获准的企业业务状态，协同人与系统，并完成可验证的工作。近期路径：进入真实现场，通过一条工作流证明价值，再逐步提炼可复用能力。

| 事项 | v0.1 的侧重 | v0.2 的补充 |
|---|---|---|
| 项目定位 | 可复制的改造方法与交付体系 | 补齐企业 Context、工作状态与协作运行时的长期构想 |
| 现场交付 | 诊断、流程交付、持续改进 | 明确 FDE 是起步方式，终局产品形式仍未定 |
| 技术能力 | 共享知识、角色和流程、验证与沉淀 | 区分 Kernel、行业包、企业配置、共享工具与内部资产 |
| 协作与治理 | 责任、权限、人工复核 | 补齐个人/岗位/组织边界、状态冲突、双调度与撤权 |
| 阶段路线 | 首轮试点与标准化交付 | 明确每阶段证据、停止条件及远期网络研究的独立性 |
| 文档状态 | 当前研究形成工作方案 | 统一导航，区分用户授权、历史原则、建议与假设 |

本版整合资料后的推导不等于用户逐项批准。没有把任何行业、供应商、数据库、界面或产品名称锁定为实施方案。

## 2. 双层能力框架

### 2.1 面向客户的七项交付能力

| 能力 | 最小交付物 | 验收问题 |
|---|---|---|
| 现场诊断与机会筛选 | 流程、角色、系统、痛点、基线与候选排序 | 是否值得改、是否应先处理其他问题？ |
| 企业知识与 Context | 来源清单、有效规则、权威状态、冲突与更新责任 | 能否解释每项关键结论从何而来？ |
| 岗位与工作流交付 | 输入、输出、状态、交接、异常和完成标准 | 是否减少整条流程的负担？ |
| 身份、权限与责任 | 数据准入、可见范围、审批和动作清单 | 谁能看、谁能改、谁承担责任？ |
| 质量、价值与成本评价 | 固定任务、失败样本、基线对照与总成本 | 效果是否可信、是否值得持续使用？ |
| 反馈与复用沉淀 | 审阅后的规则、模板、评价集与版本记录 | 下一次交付是否更快、更稳？ |
| 使用、交接与退出 | 操作说明、维护责任、培训、导出与停用方案 | 没有交付人员驻场能否继续工作？ |

### 2.2 候选技术结构

共享工具 → 稳定 Kernel 契约 → 行业语义与评价 → 企业配置和 Context → 任务与人机协作 → 受控行动与反馈。

需要保留来源/时间、事实/推断分层、状态与规则版本、确定性授权和核验接口。具体存储、调度、模型、连接器和 Agent 框架根据用例比较；先用最小实现验证契约，重复出现后再抽象。详见[分层架构](../02-架构与方法/Kernel与企业Context分层.md)。

## 3. 首轮建议边界

- 一家明确授权的企业、一条工作流、一位业务负责人；涉及其他岗位时逐一明确参与和权限。
- 选择频率足够、有可获取样本、结果可判断的工作。报价资料整理、文档交付、采购状态跟进只是候选，尚未选择。
- 先只读或生成草稿；如需正式写入、外发或承诺，单独定义具体授权与验收，不从研究授权推导。
- 知识与业务状态分别管理；个人隐私、私人聊天和跨客户资料不作为默认输入。
- 不在首轮默认建设全企业本体、统一 Runtime、多节点网络、绩效系统或替换全部现有软件。

## 4. 分阶段路径与阶段门槛

| 阶段 | 工作与产物 | 进入下一步的条件 | 暂停或调整条件 |
|---|---|---|---|
| P0 业务发现 | 确定用户/采购/安全角色，画流程与系统图，收集获准样本，记录基线、完成态与禁区 | 痛点、责任、材料权利、评价方法清楚，形成 GO/HOLD/NO-GO 记录 | 无授权入口、结果不可判定、简单工具已足够或价值不足 |
| P1 只读/草稿验证 | 用固定任务比较现有方法、规则与 AI；记录来源、冲突、修正和成本 | 关键结果可追溯，净负担与价值优于基线，业务负责人接受边界 | 错误不可发现、纠错成本抵消收益、权限难以界定 |
| P2 限定现场使用 | 在获准人群和材料范围内运行，建立维护、交接、停用机制 | 持续使用具有可信价值，运行成本和人工支持可承担 | 依赖交付人员持续救火，异常积压或使用负担上升 |
| P3 受控执行（按需） | 明确目标、动作、版本、批准、幂等、回执、恢复/补偿；先模拟再执行 | 每类动作单独获得授权，故障与撤权验证有效 | 无法判定部分成功、无法限制外部承诺、恢复责任不清 |
| P4 第二场景/组织复用 | 记录差异、工时和维护成本；提炼行业包、配置与共性能力 | 有独立需求，客户隔离有效，复用降低交付成本 | 永久客户分支增加、每次重写、复用侵犯数据或产权 |
| P5 产品化与运营 | 选择交付/软件/平台组合，明确服务等级、价格、许可证和持续支持 | 实际采购、持续使用、可靠性及单位经济性证据支持 | 收入不能覆盖持续成本，产品边界无法稳定 |

P3 并非 P4 的必需前置：只读能力也可以复用。现有规则和软件已满足需求时，可以保持较低自治等级。多节点联邦、Role Agent、组织演化另立研究，不是 P5 自动包含的功能。

## 5. 首个企业的参考节奏

延续 v0.1 的约 90 天试点模板，仅用于估算讨论：第 1–15 天发现与基线，第 16–30 天整理材料和准入，第 31–45 天离线验证，第 46–70 天限定现场使用，第 71–90 天验收、交接和复用复盘。

该模板不代表已排期、已签约或必然需要 90 天。开始时间、工期和人力依赖目标流程、材料质量、系统访问、采购和安全审查；每个阶段需先过证据门槛。HA7CH 的短周期现场演示可用于发现问题，不能代替稳定性和持续价值验证。

## 6. 评价与验收

在 P0 建立指标定义、样本范围、测量窗口、验收人和目标值；当前不编造统一达标比例。

| 维度 | 建议观察 | 需要避免的误判 |
|---|---|---|
| 业务结果 | 完成率、端到端时长、遗漏、返工、等待及异常闭环 | 仅凭生成速度证明整体提效 |
| 质量与可信度 | 关键状态准确性、证据可追溯、冲突暴露、纠错成本 | 把抽取成功率等同事实正确率 |
| 人的净负担 | 人工查找、复核、纠错、维护与被打断时间 | 把通知数、消息数、Bot 数当价值 |
| 权限与执行 | 不应可见的内容、未授权动作、撤权、重复执行及恢复结果 | 只看正常演示，不检查失败路径 |
| 总成本 | 模型/工具、集成、人工审核、现场交付、维护和支持 | 把“零 Token”理解为整体零成本 |
| 复用 | 第二次的配置、实施工时、改代码量和持续维护 | 模板多即产品化 |

净工时变化应包含新增加的复核、纠错和维护负担。业务收益无法归因时使用区间或定性记录，不能直接转成收入预测。保留失败与退出样本。

## 7. 角色与运行责任

需要业务负责人确认规则、完成态与例外；交付负责人维护范围和证据；数据/安全责任人确认准入与权限；使用者检验实际负担；技术维护者负责版本、回执和故障处理。这些是职责清单，不等于必须新增五个岗位，实际可由明确人员兼任。

通过审阅后才把现场纠错变为正式规则。每次规则更新注明来源、版本、影响范围和恢复方式；进行中任务保留所用版本。交接必须能指出谁维护资料、谁处理异常、如何导出和停用。

## 8. 商业与产品化判断

首批客户应有明确业务、真实负责人和可验证需求；“其原有商业模式成立”是目标客户画像假设，并非本项目商业模式已验证。

价值指标和计费单位分开。按项目、服务、使用或结果收费都需实际采购、归因和成本证据。产品选择包括持续交付、行业软件或 Context/协作产品，当前保留选项。

在采用 HA7CH 或其他公开实现前核验精确版本、许可证、依赖、身份权限和运维条件。已完成理念研究不意味着代码已适合生产使用。

## 9. 当前下一步：先补齐六个决定

1. 首个可进入的企业与业务负责人是谁？本项目先服务内部还是外部客户？
2. 首条工作流的触发、输入、完成态和异常边界是什么？
3. 获准材料有哪些，权威记录在哪里，谁处理冲突和更新？
4. 与当前办法比较什么，基线、样本、目标和验收人如何确定？
5. 哪些只读/草稿能力足够，哪些具体动作确需实施授权？
6. 可用人力、预算、期限、维护与退出责任是什么？

六项形成一份场景说明和 GO/HOLD/NO-GO 记录后，再提出与真实场景匹配的技术方案。当前文档整合不替代上述业务决定。
