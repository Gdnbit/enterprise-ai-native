# 企业通用 AI Native 改造项目整体方案

版本：v0.1。日期：2026 年 11 月 3 日。状态：供项目讨论与决策的工作方案。

本方案整合已有的 [ANC 综合研究](../research/2026-11-03-anc-report.md)与 [HA7CH 专题研究](../research/2026-11-03-ha7ch-report.md)。本版形成项目定位、能力框架、交付方式和落地路线；当前仅进行文档规划。后续实施安排是路线建议，启动开发需有新的明确任务。

## 1 项目定位

**本项目面向企业建立一套可复制的 AI Native 改造方法与交付体系：进入真实业务现场，找出值得改造的工作流程，使人与 AI 在共同的知识、规则和权限下完成任务，并通过业务结果持续改进。**

建议项目从“现场诊断 + 流程交付 + 持续改进”起步，在真实项目中沉淀企业共享的 AI 能力，经过复用验证后再确定产品化范围。

### 1.1 项目要解决的问题

企业的工作可能分散在文档、表格、聊天和业务系统中。员工即使能够使用 AI，也可能仍需反复寻找背景、转述需求、搬运结果和等待确认。对具体企业，这些问题是否存在、造成多大损失，需要通过现场诊断确定。

本项目围绕四类问题展开：

- **信息问题：** 事实分散、口径不一致、资料过期，完成任务需要频繁找人确认。
- **流程问题：** 重复录入、交接等待、异常无人跟进，单个步骤提效后整体交付仍慢。
- **执行问题：** AI 产出无法直接进入业务，任务状态、复核责任和实际动作脱节。
- **积累问题：** 经验留在个人脑中或聊天中，人员变化后难以接续，重复错误未形成改进。

首轮目标是验证其中一个具体问题，并完成一条可验收的业务流程；中期目标是让相邻工作复用知识和方法；长期目标是逐步改变企业组织工作的方式。

### 1.2 服务对象与使用者

| 角色 | 项目需要为其提供的价值 |
| --- | --- |
| 企业决策者 | 看清优先投入方向、成本、依赖、责任与实际结果 |
| 业务负责人 | 获得可管理、可验收的工作流程，能够处理例外和确认交付 |
| 一线人员 | 在已有工作方式中减少查找、搬运和重复处理，得到可用的帮助 |
| 知识与技术维护人员 | 有依据地更新资料和规则，掌握权限、运行状态与故障处理 |

项目可以先在自有企业或获授权的合作企业试点。**是否对外提供商业服务，尚待用户确定。** 本方案用“目标企业”统称两种情形；若选择对外服务，再补充合同、客户交接与持续服务安排。

### 1.3 什么是本项目的通用性

通用性来自可复用的诊断步骤、场景说明、知识规范、人机分工、权限控制、评估方法和交付管理。具体企业的业务规则、资料、系统连接、专业判断和验收标准需要单独配置。

对组织演进，本项目采用分层目标：

| 层次 | 形成什么能力 | 完成标志 |
| --- | --- | --- |
| 个人工作 | 员工能利用 AI 完成岗位任务 | 能解释结果依据、检查交付并处理缺失信息 |
| 流程协作 | 多个步骤及责任人连接起来 | 从触发到交付可跟踪，异常可接管 |
| 组织积累 | 多个场景使用共同事实和方法 | 经验可维护、可复用，改进能被验证 |

组织层级和岗位是否调整，取决于原有职能能否被可靠承接；首轮验收不以减少人数或管理层为目标。

## 2 从两份研究中采用的原则

| 研究依据 | 本项目采用的做法 | 适用条件与取舍 |
| --- | --- | --- |
| ANC 强调经营方式与人机分工 | 按业务流程组织改造，保留结果责任人 | 用实际交付判断，不以工具数量判断成熟度 |
| HA7CH 的 FDE 现场方法 | 同时理解经营目标、一线工作和实现条件 | 问题定义与企业确认，专业判断由相应人员承担 |
| 全景观察与局部验证 | 先看依赖，再选择一条工作路径验证 | 控制首轮范围，防止只做演示或过早铺开 |
| 个人 AI 与共享组织知识 | 岗位使用方式可以不同，关键事实和方法共同维护 | 共享范围服从人员与数据权限 |
| 经验沉淀为 Skills 与评估 | 将步骤、案例、错误与检查方法版本化 | 修改需复核，不能把任意生成结果当成事实 |
| 知识与任务状态分开 | 资料记录依据，任务记录执行与确认 | 交易与审批继续尊重业务系统的权威记录 |
| 多轮任务冻结规则版本 | 每项持续任务能追溯使用的规则与依据 | 中途更新需要明确迁移与责任人确认 |
| 诊断与部署分阶段 | 允许继续、补条件或停止 | 演示通过后仍需完成生产验证与运行交接 |

“零 Token”用于启发复用已有 Agent 和减少重复处理，成本仍按完整任务核算。“48 小时、48 天、48 周”可帮助理解验证、沉淀和组织演进的不同尺度，排期仍由依赖与验收条件决定。“AI 改造资本”保留为远期商业模式研究，不纳入首轮交付前提。

以上是对既有研究的项目化取舍，不代表 HA7CH 的公开实现已满足本项目需求。证据和原始材料分别见 [ANC 来源清单](../research/2026-11-03-anc-sources.md)与 [HA7CH 来源清单](../research/2026-11-03-ha7ch-sources.md)。

## 3 首批目标企业与范围

### 3.1 首批企业的选择条件

建议优先寻找满足下列条件的企业，不预设行业或人数门槛：

1. 决策者支持，且有一名业务负责人持续参与。
2. 存在反复发生、影响交付的具体任务，能取得获授权的样本。
3. 能够判断输出是否合格，并建立基线和观察窗口。
4. 首轮后果可控，能够保留人工复核和接管。
5. 有人负责知识与运行维护，也愿意记录失败和修改。

缺少资料授权、责任人或可判断的结果时，先补条件。付款、人员权益、生产安全等重大决定涉及更多专业控制，不适合作为首次独立自动执行的试点。

### 3.2 首轮边界

建议首轮限定为：**一家目标企业、一条主流程、一个核心业务负责人、一小组实际使用者和一套验收标准。** 一条相邻流程作为候选，待主流程通过验收后再评估。

首轮需要形成：问题模型、当前及目标流程、任务相关知识、人机分工、权限与复核规则、可检查的交付、基线和运行结果。演示阶段可以先使用现有工具或人工配合验证流程；是否定制开发在方案设计后决定。

全公司部署、替换已有 ERP 或 CRM、复杂多 Agent 协作、完整自助平台和投资权益安排留待后续条件成熟时评估。

## 4 七项核心能力

这些是项目需要具备的交付能力，不要求在第一阶段全部开发成软件模块。

| 核心能力 | 主要内容 | 最小交付与验收 |
| --- | --- | --- |
| 企业诊断与场景选择 | 理解目标，观察任务，识别瓶颈、原因、影响与依赖 | 问题有证据，负责人确认；选中和放弃的理由可解释 |
| 企业知识与依据管理 | 整理事实、原件、术语、规则及案例，明确权威来源 | 关键答案可追溯，过期和冲突可处理，资料不足会显式提出 |
| 岗位 AI 与流程交付 | 让员工获得必要背景，将处理、复核、交接与结果连起来 | 真实任务能交付，接收方能验收；状态与实际结果一致 |
| 身份 权限与责任 | 明确谁可读、谁可改、谁批准、谁接管 | 后端或业务系统限制动作，越权被拒绝，重要行为有记录 |
| 质量评估与价值测量 | 使用真实样本，对照基线检查正确性、总投入和业务效果 | 既检查成功也检查失败，收益不重复计量，结论有适用范围 |
| 反馈与复用资产 | 将人工修正归类，更新方法与样例，控制版本和发布 | 修改可复核、可回退，对新旧任务的影响可解释 |
| 组织采用与运行交接 | 岗位培训、明确负责人、异常处理、维护与复盘 | 员工会用且知道何时转人工，业务方能够持续接手运行 |

个人助手用于理解、准备和检查岗位工作；流程执行器用于持续推进可定义的任务；共享知识服务提供获授权的事实和方法。三者可以组合，不强制每个人都配置独立 bot，也不要求所有任务进入同一聊天入口。

## 5 交付体系与可复用资产

### 5.1 三个交付层次

**方法与模板。** 形成诊断、流程设计、知识准备、权限、评估、成本和运行的统一做法，使不同项目能比较和复盘。

**企业现场交付。** 由具备业务沟通、产品定义与实现判断能力的人员进入现场，对接领域专家和业务负责人，把方法落实为可验收结果。项目复杂时由团队分工承担这些职责。

**共享运行能力。** 随已验证的流程需求，逐步配置知识、身份、任务、连接和评估能力。优先复用现有系统；有清晰必要性和维护能力时才建设定制模块。

### 5.2 每个试点必须留下什么

| 交付物 | 必须包含的内容 | 主要确认人 |
| --- | --- | --- |
| 企业诊断与问题模型 | 瓶颈、因果假设、量化影响、相关方、已有尝试和证据状态 | 决策者与业务负责人 |
| 流程与场景说明 | 触发、输入、输出、适用范围、人机分工、异常及停止条件 | 业务负责人 |
| 最小知识清单 | 原件、规则、来源、权限、版本、有效期和维护责任 | 知识负责人 |
| 交付与控制方案 | 使用入口、系统依赖、允许动作、复核、任务状态与接管 | 业务及技术负责人 |
| 评估与价值记录 | 样本、基线、失败、质量、人工投入、周期和全部相关成本 | 业务负责人及复核人 |
| 运行与改进手册 | 日常使用、异常处理、知识更新、版本变更、恢复和退出 | 运行负责人 |
| 阶段结论 | 已完成、未完成、剩余依赖，继续或停止的理由 | 阶段验收人 |

跨企业可复用的是方法、模板和经审查的一般能力。目标企业的私有资料、人员记录、访问权限与商业承诺保持隔离。第一家企业的成果只有在相邻流程或第二家企业得到验证后，才标记为具备相应复用范围。

## 6 首轮验证场景

### 6.1 候选场景的选择

| 候选方向 | 可交付结果 | 需要具备的条件 |
| --- | --- | --- |
| 询价与报价准备 | 已核实的报价草稿、缺失信息及待确认事项 | 产品、价格与交期依据明确，有商业复核人 |
| 单据处理与核对 | 结构化信息、差异清单和原件依据 | 有脱敏样本、字段规则和正确结果 |
| 项目或采购进度整理 | 基于实际记录的进度、阻塞与负责人清单 | 任务记录可信，进度定义清楚 |
| 岗位知识服务 | 带有效依据的答案或转交负责人 | 高频问题与有效制度可用，有维护责任 |

最终选择由诊断决定。单纯问答可以作为入口，但应确认它解决了什么工作问题；涉及多个环节时，验收覆盖到接收方确认结果。

### 6.2 用报价准备说明完整交付

以“从收到询价到形成已复核的报价草稿”为示例，暂不作为已选定需求：

1. 销售提供询价，系统或人员确认客户、产品、数量与缺失信息。
2. AI 在授权范围内读取有效资料和系统状态，说明所用依据与时间。
3. 确定性规则负责金额等计算，AI 组织草稿并列出需确认的折扣、交期与条款。
4. 业务负责人检查，退回修改或确认交付；对外发送作为另行授权的动作。
5. 保存最终版本、确认人与修改原因，跟踪后续错误和返工。

```mermaid
flowchart LR
    A[真实任务与明确负责人] --> B[获授权的知识与系统依据]
    B --> C[AI 与规则处理]
    C --> D[检查 复核与异常接管]
    D --> E[接收方确认交付]
    E --> F[记录结果与人工修改]
    F --> G[审查后改进知识 方法与评估]
    G --> B
```

验收同时覆盖报价依据、计算、总处理时间、人工复核和返工。资料过期、同名客户、缺价格、接口不可用、重复询价和复核拒绝均应纳入观察。该示例也适用于说明单据、项目及其他流程如何形成闭环。

## 7 项目建设的分阶段路径

项目建设与单家企业交付分开管理：前者证明我们能否形成可复制的体系，后者证明某次改造是否有效。不能用一个成功演示同时宣告两者完成。

### 7.1 项目整体建设路径

| 阶段 | 目标 | 主要交付 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| 阶段一 明确项目与首个对象 | 确定内部试点或对外服务，找到可进入的企业 | 定位确认、对象与负责人、可用资料和约束、诊断计划 | 真实企业愿意配合，数据和访问范围明确 |
| 阶段二 跑通首个流程 | 证明一个具体改造能持续交付 | 现场诊断、目标流程、小范围运行、验收与运行交接 | 质量达到约定要求，价值可解释，运行有人负责 |
| 阶段三 验证复用范围 | 分清共用能力与企业特有内容 | 在相邻流程或第二家企业复用，记录新增配置和投入 | 复用范围有证据，质量保持，维护成本可承担 |
| 阶段四 形成标准交付 | 使交付可以由更稳定的团队接续 | 模板、职责、培训、成本模型、版本与项目管理机制 | 其他交付人员可按规范完成相近项目，责任边界清楚 |
| 阶段五 扩展产品与组织能力 | 根据使用积累选择产品化方向 | 场景包、共用服务或自助能力，以及持续运营方式 | 真实需求反复出现，投入与单位经济性支持扩展 |

本次交付处于阶段一的方案整理部分；尚未选定试点企业。后续阶段逐项立项，不因文档中的路线而自动启动。

### 7.2 单家企业的约 90 天参考节奏

以下沿用综合研究的参考节奏，以企业持续配合、资料可用、系统依赖可解决为前提。时间是讨论排期的起点，进入下一阶段以条件达成为准。

| 阶段 | 参考时间 | 必须完成 | 验收或决策 |
| --- | --- | --- | --- |
| 诊断与选题 | 第 1—15 天 | 观察工作，形成问题模型、流程图、基线与试点选择 | 企业确认问题、负责人、范围与价值假设；决定继续、补条件或停止 |
| 流程与知识准备 | 第 16—30 天 | 明确目标流程、依据、权限、复核、样例及技术选择 | 输入可用，完成条件和失败处理清楚，确认实施范围 |
| 构建与离线验证 | 第 31—45 天 | 形成最小可用交付，回放样例并观察失败路径 | 满足事先约定的质量与动作要求后，进入小范围运行 |
| 小范围真实运行 | 第 46—70 天 | 培训、限范围使用、记录全部投入和异常 | 业务方确认持续可用，未达标项有处理决定 |
| 验收与扩展判断 | 第 71—90 天 | 比较基线，交接运行，固化资产与剩余问题 | 确认继续运行、调整、退出或扩展，不把演示当作验收 |

诊断过程中可制作小演示帮助判断。演示时间不替代资料准备、生产验证和真实运行的观察时间。任务发生频率低或业务有明显季节性时，需要延长观察。

### 7.3 阶段决策与停止条件

- **继续：** 业务价值、数据条件、责任和验收方式明确，下一阶段有可交付结果。
- **补条件：** 列明缺少的资料、系统、授权或人员，指定负责人和复核日期，暂不扩大投入。
- **停止或退出：** 价值不足、无可靠数据或责任承接，或错误后果无法合理控制时，保留证据并结束该轮实施。

运行中发生严重越权、关键错误无法拦截、负责人缺位等情况，应先停止受影响动作并转人工。收益持续未达预期时重新判断场景和方案；学习阶段的投入要有可检查成果和预算边界。

## 8 责任与协作方式

| 职责 | 具体责任 |
| --- | --- |
| 项目发起人与企业决策者 | 确定目标、预算、取舍和阶段验收人 |
| 业务结果负责人 | 定义合格交付、确认业务边界、协调参与人员并处理例外 |
| 现场交付负责人 | 组织访谈、观察、方案和实施，把问题与交付连接起来 |
| 知识与领域负责人 | 确认事实与规则，维护有效期，承担相应专业判断 |
| 技术与运行负责人 | 管理系统接入、身份、状态、监控、恢复与交接 |
| 质量复核人 | 按样例和真实结果检查，报告错误、偏差和剩余风险 |
| 一线使用者 | 参与验证，反馈不合用之处，按约定完成复核与接管 |

小项目可以兼任；涉及重要审批与动作的职责分离要求按企业制度执行。每项跨部门结果指定一名直接责任人，并说明其授权范围、期限、资源和升级通道。临时责任安排不能掩盖预算、人员管理和专业标准仍需长期有人承担。

培训以岗位真实任务为中心：怎样给出信息、识别依据、检查结果、提出例外、退回与转人工。记录实际使用与失败用于改善工作，不以提示词数量、Token 消耗或简单活跃度给员工排名。

## 9 验收与价值衡量

### 9.1 首轮是否成功

试点开始前，业务方与项目组共同确定任务范围、质量底线、比较基线、样本、观察窗口及验收人。质量和控制是进入运行的条件，不能用提速抵消严重错误。

| 维度 | 观察什么 | 判断方式 |
| --- | --- | --- |
| 业务质量 | 事实、计算、规则和交付是否正确 | 按明确依据复核，同时检查缺资料和复杂任务 |
| 流程完成 | 是否真正到达完成条件，异常是否有人接手 | 由接收方确认，失败不从统计分母中删除 |
| 人工投入与周期 | 准备、提示、等待、复核、修改、返工及总历时 | 同类任务对照，区分人工时间与经过时间 |
| 完整成本 | 工具、模型、集成、培训、知识和运行维护 | 计入相关人员投入与初始投入，说明分摊口径 |
| 业务价值 | 节省时间用于何处，是否减少外包、避免增员或增加合格交付 | 将容量释放与实际兑现分别报告 |
| 持续运行 | 维护、版本、故障和退出能否被接手 | 运行人员按手册演练并确认责任 |

具体目标数值在取得企业基线后确定；此处不预设“必须提效多少”。主观满意度、AI 使用量和生成数量用于解释结果，不能替代业务验收。

### 9.2 项目本身是否具备复用价值

第二次交付还应检查：复用哪些资产、增加哪些配置、现场与维护用了多少人时、哪些规则重新设计，以及结果是否保持。只有能说明复用条件与成本，才能决定建设标准产品或扩大服务。

## 10 技术与商业路线的当前取舍

### 10.1 当前确定到能力层

工作入口优先贴近已有办公和业务环境；知识保留权威来源；重要动作由受控接口和审批约束；长任务需要可恢复状态；质量和反馈可追溯。人员、企业和数据之间的隔离随实际范围明确配置。

具体使用办公套件、低代码平台、定制系统、本地部署还是混合方案，在目标流程与约束明确后比较。同一组真实样例和验收标准用于比较候选方案。Markdown、数据库、检索方式和模型品牌均不是本版预先锁定的答案。

HA7CH 的开源代码可进入后续候选评估，采用前另核对完成度、许可证、依赖、身份与权限、可靠性和运行成本。本项目的知识层与执行层不以其现有实现为必要条件。

### 10.2 若转向对外服务

建议按诊断、实施和持续维护分别明确范围、交付、费用与责任。具体定价来自实际成本、价值与服务条件，不沿用外部案例报价。服务方需要提供文档、资料与配置导出、账号与权限交接，以及退出时的处理方式。

投资、股权或结果分成可以作为未来独立议题，不能用潜在回报替代交付预算与维护责任。若先做内部改造，同样记录成本与验收，只暂不设计对外交易结构。

## 11 主要依赖与边界情况

| 情况 | 对项目的影响 | 处理原则 |
| --- | --- | --- |
| 目标与现场描述不一致 | 容易实现错误需求 | 保留假设与证据，由业务方共同修正 |
| 资料过期或相互冲突 | 输出可靠性下降 | 指定权威来源，冲突未解决前不强行给确定结论 |
| 旧系统缺少接口 | 实施与维护成本增加 | 比较人工交接、现成功能和界面自动化，重要写入另行验证 |
| 跨部门资料不能共享 | 部分流程无法直接贯通 | 按授权范围设计交接，不以共享知识为由扩大访问 |
| 多人同时修改或规则中途变化 | 状态、依据与审批可能不一致 | 明确版本、并发处理与变更确认 |
| 模型或依赖不可用 | 任务中断、重复或遗失 | 有状态记录、停止机制与人工接管，不重复执行重要动作 |
| 个人经验难以说明 | 初始规则不完整 | 用样例、现场观察与复核逐步提取，保留专家参与 |
| 节时未兑现 | 看似提效而总体价值不足 | 核查容量用途，修正收益判断和扩展计划 |

以上是方案需要处理的真实业务依赖，不替代具体企业的行业、合同与数据要求。重大专业与安全边界在试点选择和实施前由相应负责人明确。

## 12 本版方案后的决策清单

下一轮优先确定六项：

1. 先做内部改造，还是以对外服务为目标验证交付？
2. 第一家可以进入现场的企业是谁，哪些人员能够参与？
3. 企业当前最影响经营或交付的具体问题是什么？
4. 哪些资料、样本、现有系统和权限可以使用？
5. 可以投入哪些业务、领域、技术及维护人员，预算边界是什么？
6. 谁拥有首轮结果，谁能确认验收和决定下一阶段投入？

这些信息未明确前，可以继续完善诊断材料、场景说明和验收模板；不据此启动代码开发。本版的交付是可供决策的整体方案，首个企业实施方案将在获得现场证据后另行形成。
