# HA7CH 理念与企业 AI Native 改造专题研究

研究日期：2026 年 11 月 3 日。研究对象：HA7CH 的公开 GitHub 仓库、官网文章源码、课程及企业部署材料。本文是[ANC 综合报告](2026-11-03-anc-report.md)的专题补充。

## 1 研究结论

**HA7CH 对本项目最有价值的启发，是把企业 AI 改造连接成一套连续工作：FDE 到现场定义问题，围绕真实任务构建交付，再把知识、方法、权限和反馈沉淀成企业共同使用的能力。** 它同时探索人才培养与长期利益机制，而不只讨论工具架构。

本项目可以优先吸收四点：

1. 在建设系统前，形成有证据、可推翻的问题模型。
2. 为员工提供个人 AI 工作方式，同时维护组织共享且受权限约束的知识。
3. 用真实使用中的错误和修改，完善可复用方法与评估。
4. 将诊断、演示、生产部署和组织变化分阶段验收。

需要保留的边界是：**“0 中层”是组织主张，“48 理论”是阶段框架，“零 Token”是成本与架构分工思路，均不是已被普遍验证的企业改造定律。** 公开仓库能提供设计、部分实现和经营者自述，不能据此认定所有能力已经产品化，或案例收益已经独立核验。

本轮主要核读 `ha7ch-home`、`ai-native-company`、`ha7ch-school` 和 `anc-diagnosis` 四个仓库；引用固定到具体提交。来源、定位和版本见[专题来源清单](2026-11-03-ha7ch-sources.md)。外部 Skill 文件作为研究材料读取，没有安装或执行，也未联系 HA7CH 或访问案例企业的私有资料。

## 2 HA7CH 的整体思路

### 2.1 从组织目标到运行基础设施

官网源码把 ANC 描述为企业共享的 AI 运行层，将业务背景、资料、项目、任务、权限、责任、人员与 Agent 连接起来。HA7CH 的公开组织介绍还包含现场部署 HDC、创作者网络 HCN、教育以及投资孵化。其 ANC 用语既指 AI Native Company 的方向，也指支撑这种公司的共同运行能力，阅读时应区分。[H01](2026-11-03-ha7ch-sources.md#h01)

可以将相关工作理解为三层：

| 层次 | 主要问题 | 对本项目的意义 |
| --- | --- | --- |
| 组织理念 | 公司如何安排信息、工作与责任 | 定义改造方向和判断标准 |
| 现场交付方法 | 谁理解问题，怎样做出业务结果 | 形成诊断、试点、部署和复盘流程 |
| 工具与知识基础 | 人和 Agent 如何共享资料、方法及执行状态 | 支撑多个场景复用能力 |

这三层不能互相代替：知识服务代码存在，不代表企业已完成组织改造；有战略文章，也不代表配套运行机制已全部实现。

### 2.2 一人一 AI 与企业共享知识

`ai-native-company` 的设计以真实员工为单位配置个人 bot，角色模板提供共性，个人会话与定制保留差异；共享知识使不同人员能使用同一套组织事实和方法。运行入口优先进入已有即时通信工具，同时允许已有个人 Agent 的团队直接连接知识服务。[H02](2026-11-03-ha7ch-sources.md#h02)

这提示我们，个人提效与组织积累是两个需要同时设计的目标。员工可以有不同工作台，但关键知识不能只存在于私人聊天记录里；共享也不等于所有员工能看全部资料。

本项目不必把“一人一 bot”规定为唯一技术形态。个人助手、岗位助手和流程执行器可以并存，选择依据应是任务归属、权限、协作与使用成本。

## 3 FDE 如何把模糊需求变成可交付结果

### 3.1 Echo 与 Delta

HA7CH 的课程用 Echo 和 Delta 描述 FDE 的两种能力：前者进入现场识别真实问题，后者将问题端到端实现为可使用的结果。它强调 FDE 应参与问题定义，交付终点应接近业务结果，而非仅完成已有需求清单。这是 HA7CH 的人才与交付口径，不是所有机构对 FDE 的统一定义。[H09](2026-11-03-ha7ch-sources.md#h09)

对本项目，最有用的变化是把需求访谈变为现场判断：

- 与决策者确认经营目标、约束和投入条件。
- 跟随一线观察一项真实任务怎样完成，收集实际输入、输出、等待与返工。
- 比较管理者描述与现场事实，必要时共同修正问题定义。
- 用真实样本制作一个可检查的小交付，验证是否改善工作。

FDE 可以主动质疑表面需求，但业务目标、权限和验收仍需与企业责任人确认。能快速生成程序，不代表可以独立作出行业专业判断。

### 3.2 客户九宫格的价值与局限

课程将商务、产品、研发三种能力，与偏向降本、组织进步和战略改造的客户类型交叉。其有用之处在于提醒交付者同时处理购买动机、流程设计和工程实现；组织越复杂，所需协作与治理一般也越多。[H10](2026-11-03-ha7ch-sources.md#h10)

课程中的约 30 人、约 200 人和大型国央企是经验性分类，不能直接作为我们识别客户的规则。规模相同的企业也可能有不同目标；小企业同样可能处理高度敏感的数据，大企业也可能只需要一个局部工具。

本项目应改用可以现场核实的分层条件：业务目标、流程跨度、系统依赖、错误后果、决策链和维护能力。再决定由个人交付、小团队协作还是更完整的项目组织承担。

### 3.3 一面全景图与一点真实演示

HA7CH 的诊断服务材料提出同时交付企业 AI 全景图和一条真实工作流 Demo，并以 GO、HOLD、NO-GO 判断后续投入。材料将五个工作日的诊断安排与正式部署分开，明确演示不等于生产系统。[H14](2026-11-03-ha7ch-sources.md#h14)，[H15](2026-11-03-ha7ch-sources.md#h15)

这适合补强本项目的诊断交付：既让企业看见整体机会、依赖与责任，也用一个具体任务检验判断。全景图避免只解决表面问题，真实演示避免路线图脱离业务。

HA7CH 的商业报价和排期是其服务信息，不作为本项目的定价依据。我们的诊断时长应按资料、行业与现场条件另定。

## 4 企业知识与系统设计的核心理念

### 4.1 事实只维护一份 方法可以复用

架构规范要求资料带来源，易变事实在指定位置维护，角色与 Skill 引用这些事实；没有依据时明确报告尚未入库。这样可以减少在多个提示词中复制人员、日程或业务口径造成的不一致。[H03](2026-11-03-ha7ch-sources.md#h03)

对本项目，可以先建立三种资产：

| 资产 | 内容 | 维护方式 |
| --- | --- | --- |
| 事实与依据 | 规则、产品、客户、项目与原始资料 | 明确权威来源、有效期与维护人 |
| 工作方法 | 步骤、工具、例外和输出要求 | 版本化维护，变更需复核 |
| 评估样例 | 正常、缺资料、冲突、失败与越权情形 | 来自真实任务，保留预期结果和判断依据 |

这里的“权威来源”可以是文件，也可以是 ERP、CRM 或其他业务系统。订单、库存、付款和审批事实不能因为有了 Markdown 副本，就放弃业务系统中的权威记录。

### 4.2 Skills 与复利式改进

规范将日常问题、问题池、实现、审查、发布和回归评估连接起来，期望使用越多，组织方法越完善。这里的改进依赖明确的维护流程，不是模型自动记住所有经验。[H03](2026-11-03-ha7ch-sources.md#h03)

本项目可以把人工修改转化为候选改进，但先判断问题类型：是知识过期、权限不足、输入缺失、业务规则变化，还是模型能力问题。不能每次答错都机械地添加一个新 Skill，否则容易形成互相冲突的规则集合。

修改过的方法需要经过样例验证再发布，并能回退。方法、来源、工具权限与适用场景应一起维护。

### 4.3 “零 Token”的两种含义

**产品架构层面。** HA7CH 的《零 Token 设计》主张，让用户已有的 Agent 完成推理，产品承接结构化结果、版本、展示和分发；区别于产品服务器为每次操作直接调用模型。这是运行职责的分配，不是整个任务不消耗模型资源。[H11](2026-11-03-ha7ch-sources.md#h11)

**知识检索层面。** ANC 资料又用该词说明，将原件结构化保存，检索时尽量使用文件和确定性搜索，减少重复解析或额外模型步骤。[H02](2026-11-03-ha7ch-sources.md#h02)，[H04](2026-11-03-ha7ch-sources.md#h04)

两者都仍需核算用户订阅或 API、Agent 读取上下文、原件解析、存储、网络、复核和维护。文件搜索是否优于向量或混合检索，应通过目标资料与真实问题评估；不能由某个设计口号直接决定。

对本项目的设计启发是：优先复用客户已经具备的工作能力，避免为每个场景重新包装一套模型聊天界面，同时保留统一接口和结果校验。账户、许可、使用额度与服务条款在实施时单独核实。

### 4.4 客户掌握自己的运行环境

轻量方案建议每家公司在自己的 Cloudflare 账户部署知识服务；托管形态最初围绕客户常驻设备设计。这体现了把运行环境和资料控制权留给客户的倾向。[H04](2026-11-03-ha7ch-sources.md#h04)

该思路有助于交接和退出，但客户持有账户不自动解决访问、备份、数据位置或供应商依赖。服务方仍须约定谁维护、谁能进入、如何撤权、怎样恢复。Cloudflare 或某种设备只是 HA7CH 的具体选择，本项目不预先绑定。

## 5 现场试点对早期架构的修正

`LESSONS-MANUFACTURING-PILOT.md` 描述一家具备研发、产品、项目和采购四部门的医疗器械制造企业试点。企业身份和私有部署不可公开复核，因此将其作为作者披露的工程经验，而非独立效果证据。[H06](2026-11-03-ha7ch-sources.md#h06)

它最值得研究的地方是记录了早期假设不适用的情形：

| 早期假设或常见做法 | 试点提出的修正 | 本项目的应用 |
| --- | --- | --- |
| 成员已有个人 Agent，或完全依赖 IM bot | 企业可能需要先批量配置个人工作台 | 将终端准备、身份和培训纳入实施范围 |
| 同一个 bot 会话承载全部工作 | 长任务需要独立执行和可恢复状态 | 区分对话响应与后台任务 |
| 所有信息都以 Markdown 为权威 | 多轮任务和出站消息需要事务状态 | 知识与执行状态分别设计 |
| 更新方法后所有任务立即采用 | 跨多日任务中途换规则会改变口径 | 开始任务时固定规则版本 |
| 模型宣称任务完成即可回传 | 完成应由受控服务核对实际交付 | 明确业务完成条件与确认人 |
| 个人 Agent 回传工作材料 | 需要身份、去重和敏感信息边界 | 只在明确授权范围内采集与发送 |

### 5.1 知识用文件 状态用事务

这一修正补足了“文件系统承载公司知识”的适用范围。合同解释、规则和案例可以用可读文档维护；任务领取、审批、重试、完成及消息发送需要处理并发和一致性。生成一份“已完成”文件，无法单独保证业务动作已经发生。

本项目应分别维护知识依据和任务状态。需要回传消息时，保存待发送记录并可重试；模型输出只作为完成判定的输入之一。具体数据库和队列根据规模选择。

### 5.2 新版本与正在执行的任务分开

一个持续数天的任务应保留当时使用的业务规则、知识依据与审批版本。更新默认影响新任务；确需迁移中的任务时，说明变化并由责任人确认。

这也修正了“共享技能改一次，所有人立即生效”的简单表述：分发方便与执行一致性需要同时满足。

### 5.3 员工事实与绩效评价分开

试点材料明确将员工访谈用于理解工作事实，排除绩效、忙闲和能力排名。对本项目，流程诊断需要采集什么、谁能查看、如何纠正和何时删除，应提前说明。个人 Agent 能访问的历史材料，也不应默认全部用于公司诊断。

## 6 组织主张与商业模式

### 6.1 怎样理解“0 中层”

HA7CH 的文章主张，用共享背景、方法、执行、评估和动态责任人承接部分协调职能，减少以信息转述为主要作用的永久管理层；同时明确保留战略、授权、人才培养、冲突处理与风险治理。文中的 48 小时、48 天、48 周，用来描述验证业务点、沉淀能力与较长期组织重构。[H12](2026-11-03-ha7ch-sources.md#h12)

文章引用的 Block 原文确实提出重新组织信息与协调方式，并明确承认转型仍在早期。它支持“企业正在探索这种方向”，不能证明无永久中层适合所有企业或已获得稳定效果。[H18](2026-11-03-ha7ch-sources.md#h18)

本项目可先测量汇报延迟、重复汇总、跨部门等待与信息偏差，再考虑调整协调机制。DRI，即对具体结果直接负责的人，需要明确目标、期限、资源、权限和升级路径。组织是否减少层级，应由职责能否被可靠承接决定。

48 小时可以作为小范围演示的时间预算，不能承诺两天完成生产改造；48 天与 48 周也只是阶段启发。现有综合报告的约 90 天试点路线仍适用，实际节奏由依赖与验收决定。

### 6.2 怎样理解“AI 改造资本”

HA7CH 的文章提出先通过真实服务理解传统企业，再选择少数企业投入资本，并让承担改造的 FDE 获得长期权益；大多数客户仍可停留在普通项目合作。文中的投资数字被明确标为机制示例。官网说明也不把开展孵化工作等同于募资、注册完成或投资承诺。[H13](2026-11-03-ha7ch-sources.md#h13)，[H01](2026-11-03-ha7ch-sources.md#h01)

对本项目，这提供了一个关于长期激励的研究方向，但不应成为一期实施前提。先验证交付能力、持续服务价值和单位经济性；若以后考虑权益合作，再独立处理估值、归属、退出、专业尽调和利益冲突。

### 6.3 原型作为调研与六格协作策略

《MVP as Research》强调通过早期可用原型获取反馈；六格策略进一步区分目标是否清楚、方法是否明确、使用者是否具备验证能力，目标不清时先做探索并保留被否定的方向。[H17](2026-11-03-ha7ch-sources.md#h17)，[H16](2026-11-03-ha7ch-sources.md#h16)

本项目可采用有时间限制的原型来帮助业务人员表达隐性要求，但原型阶段仍应使用获授权的资料并限制外部影响。建设成本下降不代表调研、专业验证、运行和维护成本归零。不能读懂实现的人，需要可观察的行为验收和必要的专业复核。

## 7 公开实现究竟到了哪一步

本节结论来自固定提交的文档与代码静态核读，没有安装依赖、运行测试或部署。因此“代码存在”与“本轮实测通过”严格区分。

| 项目 | 本轮看见的证据 | 可以得出的结论 |
| --- | --- | --- |
| 轻量共享知识服务 | Worker 源码提供列目录、读取、搜索、写入和历史工具 | 已有具体实现可供进一步验证 |
| 写入历史与冲突处理 | 源码含历史保存及按版本条件写入逻辑 | 存在相关机制，不代表所有并发场景已验证 |
| 身份与权限 | 单公司共享 Bearer token；文档列逐成员认证为后续项 | 不能视为已具备成员级权限与可信身份审计 |
| 轻量方案端到端采用 | LIGHT-MVP 仍记录真实客户端联调及首家试点待做 | README 的 MVP 状态不能覆盖这些验证缺口 |
| 托管初始化与运维 CLI | PLAN 中多个里程碑尚未勾选；根包为私有、版本 0.0.0 | 不能将规划中的 `anc` 命令当成已发布产品 |
| 车队与制造试点 | README 和 lessons 提供生产使用自述 | 可研究经验；公开材料不足以重建私有部署或复算收益 |
| 诊断服务 Skill | 内容用于介绍服务和准备咨询 | 加载文件不等于已经执行现场诊断 |

依据：[轻量设计 H04](2026-11-03-ha7ch-sources.md#h04)、[计划 H05](2026-11-03-ha7ch-sources.md#h05)、[代码 H07](2026-11-03-ha7ch-sources.md#h07)、[包配置 H08](2026-11-03-ha7ch-sources.md#h08)、[诊断材料 H15](2026-11-03-ha7ch-sources.md#h15)。

进一步看，历史中可填写的 `author` 是调用参数，当前共享 token 并不能独立确认填写者身份。若用于敏感企业资料或规则修改，需要增加可信成员身份与服务端授权。提示词要求“按角色访问”不能替代这些控制。

公开资料中的“首个”“无人占位”“定制成本接近零”等强表述，不作为本项目的市场事实；竞品、订阅许可、价格和可用能力也不从其对比表直接外推。

## 8 对现有项目方案的具体补充

### 8.1 保留已有方向 增加运行细节

| 现有综合报告方向 | HA7CH 带来的补充 | 本项目建议 |
| --- | --- | --- |
| 以具体流程改造为单位 | 现场判断与问题模型 | 记录瓶颈、因果假设、影响、相关方和已有尝试 |
| 知识有来源与版本 | 易变事实单点维护 | 为关键事实指定权威位置，引用代替手抄 |
| 人工反馈进入改进 | Skill 与评估的发布闭环 | 明确问题归类、修改人、复核人和回归样例 |
| 任务与动作受控 | 对话与执行分离、事务状态 | 长任务可恢复，完成判定独立于聊天表述 |
| 治理随风险配置 | 会话内规则冻结 | 保留任务使用的版本，迁移需确认 |
| 分阶段验收 | 全景图、真实演示与三种退出判断 | 诊断后决定继续、补条件或停止 |
| 组织与能力配套 | 动态 DRI 与专业培养职责 | 先承接协调职能，再讨论组织结构 |

以上是本项目对 HA7CH 的吸收方案，尚未获得目标企业验证，不代表已决定采用其开源实现。

### 8.2 下一阶段的最小交付

在确定第一家目标企业后，建议先完成以下六项，而非直接部署全公司助手：

1. **问题模型。** 写明关键瓶颈、候选原因、量化影响、相关方与已有尝试；每条标注假设、已验证或已推翻，并附证据。
2. **工作流全景与试点选择。** 看见相邻流程的依赖，同时只选一条有负责人、有样本、能判断结果的工作路径。
3. **最小知识结构。** 整理任务所需事实、原件与规则，明确权限、维护人和有效时间。
4. **真实样本演示。** 贯通输入、处理、人工检查和输出；使用者现场指出错误与缺失。
5. **验证记录。** 记录基线、总人工投入、错误、失败退出与成本，不仅展示顺利完成的样例。
6. **继续决策。** GO 明确部署范围；HOLD 明确依赖、负责人和期限；NO-GO 说明停止理由与保留成果。

可以先用文件和现有系统形成这些产物。当确实出现长任务、多人并发或外部动作需求时，再增加事务状态、后台执行和受控集成。这样既吸收 HA7CH 的现场方法，也保留本项目按证据选择工具的空间。

## 9 最终取舍

**优先采用的方法：** 现场问题定义、整体观察与局部验证结合、事实来源治理、经验转化为方法、状态与知识分离、版本冻结和分阶段退出。

**需要试验的选择：** 一人一 bot 的具体形态、Markdown 作为哪些知识的权威来源、客户自有运行环境、已有 Agent 承担多少执行、动态责任人如何与现有管理配合。

**不能直接作为承诺的内容：** 固定 48 时间表、全流程零成本、企业必然减少管理层、尚未完成的托管工具链、案例未独立核验的效果，以及股权合作的未来回报。
