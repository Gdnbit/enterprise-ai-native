# 技术、方法论与选型原则

状态：历史经验的适用性整理 + 待验证工程建议。没有选择本项目技术栈。

## 1. 先定义工作与完成态

围绕情境、卡住的进展、期望结果、当前替代方案和选择标准开展发现。任务使用 Goal → Done Criteria → Next Action 描述。记录、分派、提交和完成验收不是同一个状态；AI 声称完成必须有业务回执支持。[S04 §2；S02 §13；S14]

发现阶段优先理解真实业务处理，避免在未知场景下提前造完整治理平台；但最小权限、敏感数据隔离、人工批准和可回退是实验前提，不因“先研究业务”而取消。[H07]

## 2. 不把概率推理变成授权

早期垂直项目的历史原则是 LLM 产生草稿，确定性业务服务授权状态变更。企业项目可借鉴这种职责划分，但旧项目 QG/BCG/Identity 边界、Pydantic AI v2 选择及其测试不自动成为本项目决策。[S14 关键决策 5、9、12、16]

每个重要动作候选记录：请求者、建议者、批准者、执行者、授权依据、读取证据、目标对象及版本、执行结果、撤销/补偿路径。重试先判断是否已执行，幂等性和错误恢复必须用场景验证。[S05 §13、23；本段幂等检查为整理建议]

早期概念设计还强调：LLM ≠ DB，Agent ≠ Rule Engine，Memory ≠ Fact，Capture ≠ Fact。采集、记忆和生成应保留候选性质、来源与确认过程，不能绕过正式写入边界。[M01]

## 3. Shared Capability 可替换

OCR、ASR、文件解析/转换、RAG、renderer、solver 和模型 Runtime 可复用成熟能力。业务契约不与 provider 输出绑定，候选结果经过校验再进入领域状态。跨模块复用和模型更换是研究方向，不预设必须自研 Harness。[S04 §16；S14 关键决策 12、16]

候选选型矩阵至少比较：任务成功率、中文/行业样本质量、延迟、成本、部署约束、可观测性、恢复、权限集成、许可与退出成本。旧来源台账中的 Docling/MinerU/Tika、Agent SDK/AG-UI/LangGraph 等只是历史线索，使用前重新检查具体版本、依赖许可与同样本评测。[S12 K01–K22]

## 4. 业务 Context 不等于通用 RAG

文档检索解决“哪里有相关内容”；业务 Context 还要知道“谁、何时、在何组织、以何权限、处于什么状态、还欠什么”。合同偏文档/版本，CRM 偏关系，项目偏任务/依赖，代码偏符号/提交，政策偏版本/权威。不要把所有对象都降成向量块。[S05 §19–20]

事件历史、状态投影、Temporal reconstruction、Ontology versioning、Source authority 和生命周期值得研究，但当前不据此批准 Event Sourcing、图数据库或特定存储方案。[S05 §23]

## 5. 渐进自治

Observe → Understand/Suggest → Draft/Dry Run → Approve → Execute → Verify → Rollback/Compensate。各业务动作分别规定风险、最大影响范围、允许条件与升级对象；自动写回复的能力不等于有权代表企业承诺价格、交付日期或合同。[S01 D37；S05 §12–13、23]

## 6. 验证应包含失败案例

建议固定一组脱敏或合成任务，同时测试正常、歧义、冲突、过期、权限撤销、恶意文档、重复执行、外部系统失败和恢复。区分事实抽取、上下文选择、建议质量、执行安全、净负担与商业结果，不能用模型回答准确率替代端到端成功率。

技术方案只在实验结论足够时通过 ADR 确认；记录选项、理由、反证、版本、许可、测试结果与重审条件。上述测试组织是本次整理建议，未作为用户已批准实现。
