# 任务中心的人机协作与 AI-native 组织设计

更新：2026-11-22。

状态：**项目长期目标已经由发起人明确确认；本文件的任务契约、协作拓扑、控制机制和评价指标属于候选设计，尚未通过真实企业试点验证。**

本文定义企业 AI-native 改造的组织层目标。它不预设裁撤岗位、改变法定责任主体、要求所有业务全天运行，也不表示项目已有生产系统。

## 1. 核心命题

**以业务任务与价值交付为基本组织单元，重新设计企业内部的人机分工、协作关系、责任体系和执行机制，使人类与 AI Agent 能够依据各自的能力、权限和风险边界动态协作，形成可持续运行、可治理、可验证、可迭代的 AI-native 企业运营体系。**

这里的“任务”不是碎片化的聊天指令，而是具有**业务目标、输入、范围、责任、依赖、约束和验收标准**的工作单元（Work Item / Work Package），并与端到端流程及正式业务对象关联。

- **目标决定工作**：首先定义要实现的业务结果，再考虑由人、Agent 或确定性服务执行哪些步骤；不以 Bot、模型调用或 Token 数量定义成功。
- **任务组织协作**：人和 Agent 可跨岗位、跨系统围绕同一工作单元合作，采用同步、异步、并行或接管等方式。
- **责任不能消失**：AI 可承担授权的执行与协调职责；业务结果、正式授权、法律义务和风险治理仍须由有权的人与组织承担。
- **工作与组织互补**：任务网络组织具体交付；职能体系保留战略、资源配置、专业培养、人员管理与治理职责，不以任务制默认取消层级。

**项目追求的不是每个岗位都有 AI，而是企业核心工作能否围绕可信状态、动态能力配置、明确责任、受控行动与可核验结果重新组织。**

## 2. 三张示意图的严谨转译

2026-11-22，项目发起人提供三张带 HA7CH 标识的示意图并确认其表达的方向为长期目标。本文件对图意进行原创文字转译；**图示不是独立测量、规范标准或普遍成立的组织定律**，也不在本仓库复制原图。

| 转变 | 设计含义 | 不能推导的结论 |
|---|---|---|
| **人机交替 → 人机解耦** | 不再默认 Agent 只能跟随人的班次执行。适合自动化的工作可在无人即时参与时异步推进；人集中在判断、授权、异常、关系与验收环节。 | 图中的“人 6 小时、AI 24 小时”只是概念示意，不等于劳动制度、可靠性承诺或真实产能倍增。 |
| **AI 在人之下 → AI 在人之间** | AI 不只是员工个人的从属工具，也可在获准范围内成为跨人、跨部门、跨业务系统的工作流协调与执行节点。 | AI 在流程图中成为节点，不等于具有独立法律人格、管理权或最终责任。 |
| **按层级分派 → 按任务/项目动态组队** | 为每项明确结果指定 DRI（直接责任人），其他参与者以 IC（贡献者）协作；同一人可在不同工作单元承担不同角色。 | 不等于员工不再有岗位、管理关系、审批链或专门的安全和专业职责。 |

这三种变化可以分别采用、逐步验证，不能假定所有业务都需要同时改变。

## 3. 组织中的责任与执行角色

| 角色 | 需要明确的职责 | 重要边界 |
|---|---|---|
| **DRI — Directly Responsible Individual** | 对某个结果的范围、完成标准、协调、验收及异常升级负责。每个关键工作单元应明确一名有权限承担责任的人类 DRI。 | 不要求亲自做完全部步骤；不能将对外责任转移给 Agent。 |
| **IC — Individual Contributor** | 贡献领域知识、资料、复核、执行、协同；可同时参加多个工作单元。 | 参与不自动授予审批权、跨域访问权。 |
| **Agent 执行/协调节点** | 在指定目的、数据权限、工具范围、预算、有效期和停止条件下执行整理、检索、提案、核对、调度等工作。 | 不自行扩大权限、覆盖正式规则或冒充组织批准。 |
| **确定性业务服务** | 身份与权限验证、规则计算、幂等写入、事务回执、结果校验、故障恢复。 | 模型生成文本不等于正式状态变更。 |
| **审批/数据/安全/运维责任人** | 在必要节点落实审批、数据所有权、职责分离、异常处置和持续运营。 | 职责可兼任但不能隐含不存在。 |

DRI 是**工作单元级的责任绑定**，不是新的永久人事职级；不同工作单元可以由不同 DRI 领导。具有法定、合同或安全意义的最终批准仍须绑定到有权主体。高风险动作按需要保留职责分离，DRI 不应自动拥有所有审批权限。

## 4. 任务契约：组织层与技术层的连接面

建议以**任务契约（Task Contract）**表达关键工作单元。以下是设计字段组，不是已经批准的统一数据库 Schema。

| 字段组 | 最小内容 |
|---|---|
| 来源与标识 | 任务 ID、触发事件、权威业务对象、来源系统、输入证据及版本 |
| 目标与验收 | 预期业务状态、交付物、质量与时间标准、验收人和完成证据 |
| 责任与分工 | 人类 DRI、IC、Agent/服务节点、交接方式、异常升级目标 |
| 依赖与状态 | 前置任务、阻塞、截止时间、当前阶段、重试和恢复机制 |
| 权限与控制 | 数据准入、可用工具、动作白名单、预算、审批条件、停止条件 |
| 可追溯性 | Context/规则版本、执行日志、审批记录、回执、纠正、质量与成本评价 |

**任务状态不等于正式业务状态。** 例如“报价草稿已生成”不等于“报价已获批准并发送”。任务可以完成某个技术步骤，却尚未达到业务验收条件。可选状态包括待准入、执行中、待复核、待批准、受阻、已验收、已取消等，具体状态机需由领域验证。

## 5. 按能力、风险与成本决定执行方式

先检查能否**取消无价值步骤、简化流程或使用确定性自动化**，再决定是否需要 AI。

| 方式 | 适用情况 | 人与系统的职责 |
|---|---|---|
| 人主导 | 高后果、模糊协商、战略决策、不可逆或敏感事项 | 人做决定，AI 只提供经核实的辅助信息 |
| 人主导 + AI 辅助 | 资料密集但需要专业判断、结果可复核 | Agent 提供材料和草稿；有权人员复核 |
| Agent 执行 + 关键节点监督 | 高频、可拆解、有明确验收与异常条件 | DRI 保持责任；阈值、冲突和不确定性触发升级 |
| 有边界的自动执行 | 风险可约束、动作可核验、有补偿或恢复策略 | 经授权自动操作；越权、冲突或失效时安全停止 |
| 确定性软件执行 | 规则明确的核算、数据校验、事务写入 | 优先使用常规软件，而非用生成式推理代替约束 |

**自治等级由动作后果、可逆性、可验证性、适用法规、风险承受能力和组织授权共同决定，不能随模型升级自动提高。** 资金、人员权益、对外承诺、隐私、生产安全和正式审批应另设控制。

## 6. 任务驱动的运营闭环

推荐的逻辑过程：

**业务事件/目标 → 有授权的证据采集和权威状态查询 → 任务契约 → 人机任务分配 → 协同/异步执行 → 复核、审批或异常接管 → 确定性动作和回执 → 业务验收 → 状态更新、复盘与知识沉淀。**

与既有架构的关系：

- **Enterprise Context** 维护有来源、时效、权限及版本的业务信息；聊天记录和模型推断不是默认事实源。
- **Task/Workflow Orchestration** 维护 DRI/IC、依赖、状态、执行节点、异常、恢复和交接；可先复用现有工作流/工单系统，不必先造平台。
- **Context Scheduler** 控制执行节点为任务有权取得且实际需要的 Context。
- **Attention Scheduler** 决定何时、因何事通知哪个人；不能让 Agent 全天运行等同于让员工全天待命。
- **Agent/Shared Capabilities** 在边界内处理语义工作；**确定性业务服务**核验权限、规则、正式写入与结果。
- **Audit/Evaluation** 维护可追溯性、纠错、风险和端到端成本，支持受控改进。

这一设计不要求替换 ERP、CRM、OA 等权威系统。更多技术分层见[Kernel 与企业 Context](Kernel与企业Context分层.md)。

## 7. 时间结构、责任制与组织边界

**异步运行不意味着无限运行。** 需要声明任务窗口、限速与预算、系统可用性、审批人下线时的等待/升级、异常值守、运行监控及安全停止。Agent 的可运行时间并非企业端到端的有效产出时间；需求不足、数据缺失、审批等待、下游瓶颈及返工都可能抵消局部速度优势。

**任务矩阵不等于取消组织管理。** 战略、人才发展、绩效管理、资源配置、劳动义务、安全合规和利益冲突仍需要明确的组织职责。目标是减少不必要的转述、重复汇报、等待与信息搬运；不能预先认定应削减管理层或员工数量。

## 8. 一个可验证的工作单元示例

以“客户询价 → 可验收的报价”为**假设场景**，并非选定的首个 MVP：

1. 由有权业务人员担任此次报价 DRI，定义范围、截止时间和验收标准。
2. 获准获取询价、产品规格、库存与报价规则；不明信息标为待确认。
3. Agent 归集材料、识别规格冲突、准备报价草稿；价格与税额优先用确定性规则计算。
4. 对折扣、交期和外部承诺等超授权事项，交相应审批人处理；没有批准不能把草稿当成正式承诺。
5. 记录交付回执、批准、更正与验收，以及人工复核、错误、时间和实际成本，复盘是否优于原流程。

该工作单元可以跨销售、采购、财务等职能，但各系统记录、专业责任和控制要求仍然存在。

## 9. 评价：从 Agent 活跃度转向业务净价值

不预设统一提效百分比，应先定义样本、基线、时间窗口、任务完成标准和验收人。

| 维度 | 观察什么 |
|---|---|
| 业务价值 | 合格工作单元完成率、端到端周期、等待与积压、客户可见结果 |
| 人的净负担 | 准备、查找、沟通、复核、纠错、异常、维护与打断的总人工时间 |
| 质量与治理 | 错误、漏办、返工、越权、未经批准动作、恢复能力和审计完整度 |
| 责任可追溯 | DRI 是否明确、依赖是否有人负责、升级是否及时、验收依据是否可见 |
| 单位经济性 | 每件合格交付的模型、工具、集成、人工、值守与长期运维成本 |
| 跨场景复用 | 第二个流程或组织的实施与维护成本、定制量和隔离风险 |

局部步骤加速可能形成新的人工审核或下游瓶颈。**24 小时在线、Agent 数量、Token 消耗与并发量都不是独立的业务成效证明。**

## 10. 决策状态与来源边界

- **已确认战略方向（2026-11-22）**：以任务和业务结果组织人机能力，研究人机异步推进、Agent 在人之间的协作节点，以及任务级 DRI/IC 责任制。
- **待验证设计**：任务契约的最小结构、具体自治级别、真实 24 小时运行条件、跨部门协调收益、责任划分与复用程度。
- **不得据此宣称**：6 小时工时制可行、Agent 24×7 稳定运行、产能按时间比例倍增、管理层必然减少、AI 获得最终法律责任，或本项目已有生产实现和客户成果。
